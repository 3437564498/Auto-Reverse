# 已确认设计边界

更新：2026-10-13（Asia/Singapore）。当前设计基线为 [V1 主方案](android-arm64-so-cpp-recovery-V1.md)。

- 目标：Android `arm64-v8a` ELF64 ET_DYN 共享库，输出可维护 C++ 重建工程。
- 工作方式：每个恢复 Job 全自动，无需人工选择函数、修复类型或修改工程；质量不足和不支持按策略自动结束并报告。
- 分析与验收：纯静态；编译/链接与 SMT 分析允许；运行目标、候选、具体执行的 Harness、仿真或设备程序不允许。
- 加固：允许部分混淆，排除需要运行时解密或生成代码的区域；影响传到相关调用/数据/入口闭包。
- Token：质量优先，不能以预算或小上下文为理由省略必要证据；保留有界终止和故障控制。
- 二创：优先 Dryxio/reagent `d12cea338c61898b06a86fe8adb25275fa9d5615` 与 ghidra-bridge `faaf05363796cbc43eac7924f3b6981cd5e40619`。
- Agent 架构：采用多 Agent、单 Agent 少量任务。默认一个 Agent 同时一份有界工作包，恢复包通常一函数一候选；Fresh 浅层树，必要短修复后轮换。
- 并发方向：用户可将 Workflow 并行 Agent 数量上限改为 **32**；V1 按32路工作者配置和验收，同时联动 Subagent/PTC 与后端全局配额。32不是已实测吞吐，当前没有修改用户实际 DSH 配置。
- 客户端/Runtime：兼容官方 DSH；客户端 MCP 与后端 SDK/Agent 执行分层。后端每 Runtime 一次一个 Job 的有界批次。
- 插件方向：通过 DSH 正式插件扩展点定制工包、证据/提案工具、批次调度、策略、取消清理和审计；定制能力属于待开发模块。
- 状态与验收：任务/候选/契约持久化，独立构建/ABI/语义检查；Agent完成不代表等价，UNKNOWN、有限、条件化和精确模型明确区分。
- 本轮授权：用户已批准六项优化，整合为V1文档及规范；同步主方案、DSH调研、范围说明和README，保留初稿快照。
- 产物：研究、方案、数据/状态契约、实施路线和验收规范，以Markdown维护。
- 当前事实：已启动 M0 开发，包含静态体检、证据对象库、持久账本、受限机器语义比较、CLI/MCP 与 DSH 插件原型；详见[实施记录](implementation-status.md)。完整恢复系统、真实模型/DSH 联调、Android NDK 链路与 32 路恢复实验仍待完成。不承诺任意库原始 C++ 完整恢复。
